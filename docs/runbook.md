# Runbook: портал відсутностей персоналу школи

**Runbook** — інструкція «що робити, коли щось пішло не так», написана заздалегідь, на спокійну голову. О другій ночі план евакуації не вигадують, а виконують. Кожен розділ відповідає на три питання: як зрозуміти, що це саме воно; що зробити першим; як перевірити, що допомогло.

Останнє оновлення: 2026-11-24. Структура — за [шаблоном набору WS11](https://github.com/koldovsky/2026-quitcode-11-devops-operations-hw/blob/main/materials/ops-kit/docs/runbook.template.md); розділ про резервні копії прибрано — бонусу ми не робили, а порожній розділ гірший за його відсутність.

**Канал алерту — issue в цьому ж репозиторії**, не чат і не бот. `smoke.yml` при червоному прогоні відкриває issue «Червоний smoke: …» (або додає коментар, якщо таке вже відкрите), а GitHub надсилає сповіщення власникові репо поштою й у вебі.

Чому так, а не Telegram, як у наборі курсу: не треба ні бота, ні секретів, тож налаштування неможливо забути; issue лишається **записом інциденту**, на який потім посилається postmortem. Ціна — алерт приходить не миттєво, а як лист. Для команди з однієї людини й продукту без нічних змін це прийнятно; для чергування 24/7 — ні, і тоді варто додати крок із Telegram із набору.

**Серйозність** визначаємо самі (матриці SEV від PM ще немає): SEV1 — прод не працює або видно чужі дані; SEV2 — зламана частина функцій; SEV3 — користувачі не постраждали.

## 1. Червоний smoke

**Як зрозуміти:** у репозиторії з'явилося issue «Червоний smoke: <середовище> <коміт>» із посиланням на прогін.

1. Відкрити прогін → крок smoke → рядки `::error::`:

Три перші рядки починаються однаково — розрізняє їх **хвіст після «—»**.

| Рядок містить | Що це | Куди далі |
|---|---|---|
| `показує <sha>, а очікувався <sha> — деплой main не пройшов чи зроблено Instant Rollback?` | прод **позаду** очікуваного | розділ 2 |
| `…, а очікувався <sha> — адреса деплою показує інший коміт` | job `deploy`: перевіряли не ту адресу (`client_payload.url`) | крок 3 |
| `…, а очікувався <sha> — не вдалося перевірити, чи новіший коміт містить очікуваний` | коміта немає в клоні прогону — зник `fetch-depth: 0` у `smoke.yml`? | крок 3 |
| `стіна входу Vercel` / `секрет обходу` | захист Vercel або `VERCEL_AUTOMATION_BYPASS_SECRET` | розділ 4 |
| `Supabase призупинено` | база на паузі | розділ 3 |
| `ключ NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | хибний ключ у змінних Vercel | розділ 4 |
| `HTTP 5xx` на `/` чи `/login` | зламаний код або змінна середовища | крок 3 |

**Новіший коміт на проді — не збій.** Job `prod` питає «чи містить коміт на проді очікуваний», а не «чи це рівно той»: за час перевірки може вийти наступний деплой. Так було в [issue #95](https://github.com/SvitlanaHaiduchyk/course-staff-management/issues/95) — два PR злито майже одночасно, прод показав новіший коміт, і перевірка на рівність прочитала це як збій, хоча `db: ok` і вхід віддавав 200. Тепер такий прогін лишається зеленим і пише в журнал рядок «новіший за очікуваний … і містить його»; червоніє прод **позаду** очікуваного — і окремо випадок, коли перевірити не вдалося (рядок «не вдалося перевірити…»): мовчазного зеленого там немає.

2. **Це ми чи провайдер?** Статус-сторінки з таблиці вище. Зелена сторінка не означає, що в нас усе гаразд (пауза бази, ліміти, наш код).
3. **Прод чи ні?** Job `deploy` — користувачі не постраждали, SEV3. Job `prod` — визначити SEV і написати PM.
4. **Спершу зупинити шкоду, потім шукати причину.** Журнали Vercel на Hobby живуть **1 годину** — потрібні рядки скопіювати в issue одразу.
5. **Розбір** — агент у профілі «лише пропонує» (розділ 7). Агент пропонує, виправляє людина.
6. **Перевірка:** Actions → smoke → Re-run → зелений; закрити issue з причиною одним рядком.
7. Після SEV1–SEV2 — postmortem `docs/incidents/<дата>-<slug>.md`.

## 1a. Червона перевірка на PR — читати лог, а не згадувати

**Урок інциденту 2026-11-23** ([postmortem](incidents/2026-11-23-prod-stuck-peer-bump.md)). Напередодні e2e справді падав через брак секретів у PR від Dependabot. Наступного дня червону перевірку `Vercel` пояснили тією самою причиною «по пам'яті» — і змерджили PR, який зламав збірку прода.

**Правило:** перш ніж пояснити червону перевірку відомою причиною, відкрити її лог і звірити **текст помилки**. Різні збої виглядають однаково в списку перевірок і зовсім по-різному в логу:

- e2e без секретів → `Немає: DEMO_USER_PASSWORD(secret)`;
- зламані залежності → `npm error code ERESOLVE`.

Якщо лог недоступний (Vercel) — відтворити локально в чистій теці:

```powershell
npm install --dry-run
```

Саме цей шлях тепер перевіряє CI (job `app`, крок «Залежності розв'язуються з нуля»), бо `npm ci` ставить lockfile і такого збою не бачить.

## 2. Відкат проду

1. Vercel → Deployments → останній **успішний** деплой → `⋯` → **Promote to Production** (або Instant Rollback).
2. Перевірити: `/api/health` показує коміт того деплою, `db: ok`.
3. Пам'ятати: відкат повертає **код**, а не схему бази. Міграцію відкотити не можна — лише нова міграція вперед.
4. Повернутися до автоматичного просування: наступний push у `main` із виправленням.

## 3. База на паузі

Безкоштовний Supabase засинає після 7 днів без запитів; `/api/health` відповідає `db: down`, `reason: paused`.

1. Supabase → потрібний проєкт → **Resume project**, зачекати 1–2 хвилини.
2. Перевірити `/api/health`.
3. **Прод і staging засинають окремо** — перед UAT, демо чи дрілом будити саме той проєкт, який потрібен.

## 4. Ротація ключа

1. Supabase → Settings → API → перегенерувати ключ; або Vercel → Settings → Deployment Protection → новий секрет обходу.
2. Оновити значення: Vercel (Production і/або гілка `staging`), GitHub Secrets — **ніколи в git і ніколи в чат**.
3. **Redeploy обов'язковий:** змінні застосовуються лише до нових збірок.
4. Перевірити smoke.

## 5. Де журнали і скільки живуть

| Журнал | Де | Скільки живе |
|---|---|---|
| Збірка й виконання Vercel | Vercel → Logs | **1 година** (Hobby) |
| Прогони GitHub Actions | Actions | 90 днів |

**Наслідок:** будь-який доказ, потрібний для postmortem, копіюємо в issue **одразу**, а не «потім подивимось».

## 5a. Помилка застосунку (Sentry)

Сюди доходять помилки, яких **не видно** в smoke: він перевіряє, що сторінка входу відкривається й база відповідає, а не що заявка подається. Помилка в server action — це для smoke зелений прогін.

1. **Sentry → Issues**, сортування за `Last Seen`. У кожній події є `environment` і `release` — тобто одразу видно, прод це чи staging і який саме деплой.
2. **`release` — це SHA коміту.** `git show <sha>` показує, який PR приніс поломку; якщо остання подія почалася рівно з нього — відкат за розділом 2.
3. **Одна подія vs потік.** Поодинока помилка в одного користувача — задача на завтра. Десятки за хвилину з одним стектрейсом — інцидент: заводьте issue, копіюйте стектрейс **туди одразу** (журнали Vercel живуть годину, див. розділ 5).
4. **Чого в події немає навмисно:** IP, заголовків, cookie, тіла запиту, параметрів адреси, входу й виходу моделі — кожну категорію вимкнено поіменно в `dataCollection` (`src/lib/observability/sentry-options.ts`). Не `sendDefaultPii`: у SDK 11 цього параметра вже немає, і він мовчки нічого не вимикав би. Якщо для розбору бракує контексту, додавайте власні теги, а не вмикайте збір: портал працює з даними працівників школи.
5. **Що саме доходить, а що ні.** `onRequestError` ловить лише винятки, що спливли. Серверні дії порталу відмову бази перетворюють на `redirect("…?error=…")` — винятку немає, тому такі випадки шле `reportDbError` (`src/lib/observability/report.ts`), і **лише** справжні збої: доменні відмови з текстами PM кидаються з `errcode = 'P0001'` і в трекер навмисно не йдуть. У події — тільки SQLSTATE і назва обмеження: текст і `details` від Postgres не передаємо, бо при порушенні `check` деталі містять увесь рядок разом із коментарем заявки. Отже, щоб побачити самі значення, потрібні журнали Supabase, а не Sentry. Що в події **є** — це стек із рядками нашого коду навколо місця збою (інтеграція `contextLines` SDK): даних людей там немає, але секрет, записаний у код рядком, туди потрапив би. Ще одна причина тримати значення лише у змінних середовища. Отже, «немає події» може означати і «немає збою», і «це була передбачена відмова» — у другому випадку дивіться журнали Vercel.
6. **Тиша в Sentry не означає, що все добре.** Перевірте, що DSN узагалі заданий: `NEXT_PUBLIC_SENTRY_DSN` у Vercel (Production і Preview). Без нього SDK мовчки вимкнений — так і задумано для локального запуску.

## 6. Staging

- Код потрапляє туди лише через `main`: PR → `main` → деплой гілки `staging`.
- Міграції — лише CI: `db-deploy-staging` (база staging) і, якщо зелено, `db-deploy` (прод). Обидва jobs звіряють ref бази з рядка підключення зі змінними `SUPABASE_STAGING_REF` і `SUPABASE_PROD_REF` і падають, якщо рядок веде не туди.
- Дані — **лише синтетичні**, акаунти `*@example.test`. Прод-дані в staging не копіюємо ніколи: staging бачать PM, усі preview і агент на розборі.
- Зламаний staging зупиняє всю команду: на ньому ж UAT і прев'ю PR.

## 7. Розбір з агентом: профіль «лише пропонує»

- Агент **читає** журнали, код і прогони й пропонує гіпотези з доказами.
- Агент **не має** права змінювати прод, бази, змінні середовища й секрети.
- Усе, що змінює стан, робить людина. Агент не бачить `.env*` — це закріплено в `.claude/settings.json`.
- Пропозиція агента без доказу з лога — гіпотеза, а не причина. Інцидент 2026-11-23 почався саме з правдоподібної гіпотези (`.npmrc`), яка виявилася хибною; лог її спростував за дві хвилини.

## 8. Чого ніколи не робити

| Ніколи | Чому |
|---|---|
| `supabase db push` з ноутбука | база розійдеться з `main`, і `db-deploy` упаде |
| `supabase migration down`, `db reset --linked` | знищують дані; резервних копій на Free немає |
| DDL у SQL Editor чи Table Editor | те саме розходження зі схемою в git |
| Копіювати прод-дані в staging | staging бачать PM, preview і агент — це витік |
| Ламати прод заради дріла | дріл — лише staging |
| Вмикати `legacy-peer-deps` замість виправлення | сховає не лише цей конфлікт, а й усі майбутні |
| Мерджити PR із червоною перевіркою, не прочитавши лог | саме так стався інцидент 2026-11-23 |
